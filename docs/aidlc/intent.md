### 6.4 ロールの扱い

依頼者による明示（2026-07-28）。

**なぜシステム側にロールを持つのか。** Discord のロール機能には次の制約があり、サークル運営で不足している。

| Discord の制約 | 困ること |
| --- | --- |
| ロールに階層構造を作れない | 「役員」の下に「会計」「広報」といった入れ子を表現できない |
| メンションで積集合を指定できない | 「Aかつ B」の人だけに通知できない。和集合しか指定できない |

**V1 の範囲**

- ロールという**概念を導入する**ところまで。
- 階層構造と、積集合による絞り込み・通知は**V1では作らない**。

**設計上の制約**

将来この2つを載せられる形にしておくこと。逆に言えば、V1 の単純さを理由に

- ロールを 1人1つに固定する
- ロールを列挙型（固定値）として埋め込む

といった、後から階層や集合演算を足せなくなる形にしない。

**決定事項**（2026-07-28）

- システム側のロールは Discord のロールから**独立**して持つ。V1では同期しない。
  - Discord 側のロール名は引き続き `community_memberships.role_names` に在籍証跡として保存するが、権限判定には使わない。
- **「管理者」はロールの一つ**とする。特別扱いしない。
- **権限はロールに紐づく**。部員に直接権限を与えない。
- **ロールは部員に紐づく**（ログインアカウントではない）。2026-09-03 決定。
  - 退部すると権限も外れる。部員でない人は権限を持てない。
  - 同じ人が Discord アカウントを作り直しても、部員として同一なら権限は保たれる。

**この決定に伴う設計上の制約**

構成としては RBAC であり定石だが、次の3点を守らないと破綻する。

1. **判定は権限名で書き、ロール名で書かない。**
   `role === 'admin'` ではなく「その権限を持つか」で判定する。
   これを守れば、ロールを増やしても階層を入れても判定側は変わらない。
   守らないと、ロールを追加するたびに全サービスの分岐を探して回ることになる。
   参考: 現状はロール名での判定がアプリ5箇所・RLSポリシー4箇所にある。

2. **ロールは行として持ち、列挙型として埋め込まない。** 後から増やせなくなる。

3. **部員とロールは多対多。** 「会計かつ広報」を後から表現できるようにする。

**ロールを部員に紐づけたことの帰結**

- 管理者になるには部員である必要がある。初代管理者も部員登録が先。
- 退部処理が権限剥奪を兼ねる。別操作にしなくてよい。
- 将来の SNS で部員以外が利用者になる場合、その人たちはロールを持てない。
  SNS 側の権限が必要になった時点で、別の仕組みを足す（いま作らない）。
- **システム管理だけを行う非部員（OB・外部の技術支援者など）は考慮しない**（2026-09-03 決定）。
  管理者は必ず部員である。この前提を設計に組み込んでよい。

**「未登録」の位置づけ（6.5 との整合）**

リアクション一覧の非部員を「未登録」と表示する決定（6.5）があるが、
ロールが部員に紐づく以上、**「未登録」はロールの値ではなく「部員行が存在しない状態」**である。

- ロール一覧に「未登録」という行を作らない。
- 表示・絞り込みの上では「未登録」として扱う（導出される状態）。

**将来詰まりうる箇所（いまは許容する）**

- 役職（会長・会計）と権限の強さ（管理者）を同じ概念にまとめている。
  「会計だが個人情報は見せない」を表現できない。サークル規模では実用上問題にならず、
  役職の引き継ぎと権限の移譲が同じ操作になる利点の方が大きいと判断した。
- 権限をロールに紐づけると、細かい差を表現するためにロールが増える傾向がある（ロールの増殖）。
  V1では権限を粗く保つことで抑える。細分化したくなったら、上の同一視が限界に来た兆候とみなす。

### 6.5 リアクション参照の確定事項

**想定する場面**（2026-09-03、依頼者による）

合宿の案内を Discord に通知し、リアクションで参加可否を集める。
リアクションした人の中に、このシステムに登録していない人が混ざる。

- **部員** … 詳細（学籍番号・緊急連絡先など）を表示する。大学提出資料の作成に使う。
- **非部員** … このシステムに登録していない人。**「未登録」として扱う**。表示できる詳細を持たない。

「未登録」はロールの値ではなく、部員として登録されていない状態から導出される
（6.4「ロールを部員に紐づけたことの帰結」を参照）。

**詳細を表示する条件**（2026-09-03 決定）

在籍している部員（`active`）だけが詳細の対象。それ以外はすべて「未登録」と同じ扱いとする。

| 状態 | 詳細 |
| --- | --- |
| 在籍 | **表示する** |
| 申請中 | 表示しない |
| 却下 | 表示しない |
| 退部 | 表示しない |
| 部員行なし | 表示しない |

理由: この一覧の目的は大学へ提出する資料の作成であり、在籍していない人の情報が混ざってはならない。
申請中・却下・退部の人はシステム上は学籍番号などを持つが、この用途では出さない。

副次的な効果として、**退部した人の個人情報がリアクション一覧から自動的に消える**。
退部処理とは別に情報を隠す操作が要らない。


- 対象は**リアクションした人全員**（部員に限らない）
- **リアクション種別で絞り込める**こと（不参加リアクションがあるため）
- 表示する詳細は学籍番号・緊急連絡先を含む。永続化する情報は現状のままでよい
- **閲覧できるのは管理者のみ**
- 部員が見られるのは「自分の情報」と「他人の公開情報」のみ
- 目的は連絡・集計、および**大学への提出資料の作成**

## 7. 設計で解く必要のある緊張関係

要求どうしが競合している箇所。どちらかを選ぶのではなく、設計で両立させる方法を決める。

### 7.1 「お手本となる」と「可換にする」— 競合しない（訂正済み）

当初これを緊張関係として記録したが、誤りだった。読み手を初学者と誤解したためである。

読み手は「ある程度できるようになった後任部員」であり、**保守を通じて実装手法を学ぶ**。したがって可換性のための抽象化は、易しさを損なう代償ではなく**教材そのもの**になる。

ただし教材として成立するには条件がある。抽象化が置いてあるだけでは学べない。

- **なぜその実装にしたのかが記録されていること**（判断の理由）
- **正しく使うために守るべき制約が明示されていること**
- 制約は文章だけでなく、可能なら型・テスト・データベース制約で強制されていること

依頼者は `CommunityProvider` を良い教材の例として挙げた。ポートを中立に保ち、プロバイダ固有の事情をアダプタへ閉じ込める構造は、そのまま「なぜ境界を作るのか」の実例になる。

この要求は成果物に直接影響する。**設計判断の記録（ADR）は任意ではなく必須**である。

なお、抽象化を無制限に増やすことは別問題として避ける。差し替える対象にのみ適用し、予防的な抽象化は作らない。

### 7.2 非部員のリアクション表示 — 解決済み

リアクションした人が部員でない場合、学籍番号も緊急連絡先も存在しない。

**回答: ロールを「未登録」として扱う。** 行を分けるのではなく、同じ一覧に並べたうえで未登録と分かるようにする。絞り込みの対象にもなる。

### 7.3 「サークル専用SNS」の利用者範囲 — 部員に限らない

SNS の利用者には**部員ではないが興味のある人**が含まれる想定。ただしまだ構想段階であり、いま作らない。

設計上の含意: 「システムの利用者は必ず部員である」という前提を、取り消せない形で埋め込まないこと。
現在この前提は既に部分的に崩れている（リアクションした非部員を「未登録」として扱う）。
