## 3. 決定と衝突している実装

`intent.md` 6.4 で決めた制約に、既存コードが違反している箇所。

### 3.1 権限判定がロール名で書かれている（19箇所）

決定では「判定は権限名で書き、ロール名で書かない」としたが、現状はすべてロール名。

| 場所 | 箇所数 |
| --- | --- |
| `member/src/api_v0/member/service.ts` | 5 |
| `community/src/api_v0/message/service.ts` | 4 |
| `community/src/api_v0/user/id/service.ts` | 3 |
| `community/src/api_v0/user/service.ts` | 2 |
| `community/src/api_v0/user/id/role/service.ts` | 1 |
| `community/src/auth/better-auth.ts` | 2 |
| `*/src/core/auth.ts` | 2（判定ではなく正規化） |
| `frontend/src/middleware.ts` | 1 |

RLS ポリシー側にも `current_setting('app.current_user_role') = 'admin'` が4箇所ある。

ロールを追加すると、これらすべてを探して直すことになる。

### 3.2 ロール変更APIが未実装のまま存在する

`community/src/api_v0/user/id/role/service.ts`:

- `updateUserRolesService` — 権限チェックだけ本物で、**戻り値はハードコードされたモック**。呼んでも何も変わらない。
- `getUserRolesByIdService` — **Discord のロール**を返す。システム側のロールではない。決定「Discord から独立」と整合しない。

ルーターに登録されている形跡もない。

### 3.3 ロールが部員ではなくアカウントに紐づく

`app_accounts.role` は `user` / `admin` の2値で、ログインアカウント（`user_id`）に付く。
そのため次が起きる。

- 部員でない人が管理者になれる
- 退部しても権限が残る（退部処理と権限剥奪が連動しない）
- 同じ人が Discord アカウントを作り直すと、部員としては同一でも権限が失われる

`intent.md` 6.4 で **ロールは部員に紐づける**と決定済み。移行が必要。

### 3.4 非部員と非在籍者の表示区別がない

リアクション一覧には非部員も並ぶが、区別する表示がない。
`intent.md` 6.5 で「在籍者のみ詳細を表示し、それ以外は未登録として扱う」と決定済み。

なお表示に必要なデータは既にある（`memberStatus` を `null` 許容で保持済み）。
不足しているのは表示側の分岐のみ。

## 4. 満たされている設計（維持すべきもの）

要求「お手本となること」に照らして、既存の良い部分を明示する。壊さないため。

| 仕組み | 内容 |
| --- | --- |
| 認証境界 | `app_auth` と `public` の間に外部キー0本。連結は `app_accounts.user_id` の値のみ |
| 個人情報の遮断 | 名簿は `app_api.member_directory_entries` ビュー経由のみ。非公開列は存在しない |
| 権限の偽装拒否 | アプリが渡す `SET LOCAL` の role を、トリガーが `app_accounts` の実値と突き合わせる |
| 追記専用の履歴 | `member_status_history` はトリガーのみが書く |
| 最小権限の接続 | `app_runtime` が条件を満たさなければ起動時に接続を拒否 |
| プロバイダの可換性 | `CommunityProvider` はポートを中立に保ち、Discord 固有の事情をアダプタに閉じ込める |
| CSV 出力 | 数式インジェクションを無害化してから出力する（`=`,`+`,`-`,`@` 始まりのセルを引用符付与） |

`CommunityProvider` は依頼者が教材として良いと評価したもの。この形を他の境界にも適用する。

### 4.1 CSV 出力の詳細

最優先の要求「大学に提出する資料に必要な情報をすぐ取得できる」を担っている実装。

- 場所: `frontend/src/app/event/[id]/memberTableUtils.ts`（`buildReactionMembersCsv`）
- 起点: イベント詳細のリアクション一覧。管理者のみ到達できる
- 列: 名前・公開表示名・部員状態・学年・学籍番号・学生メール・緊急連絡先・保険加入・アレルギー・アレルギー詳細・スキル・興味・現在の活動・自己紹介・Discordニックネーム・Discordロール・Discordユーザー名・DiscordユーザーID・リアクション・メンバーID・ユーザーID（21列）
- 対象: 画面で絞り込んだ後の行（`table.getRowModel()`）
- 安全対策: 表計算ソフトが数式として解釈しうるセルを無害化してから書き出す

**制約**: 出力の起点が「イベントのリアクション」に限られる。
イベントと無関係に「全部員の一覧」を出す経路は存在しない。要件化の際に、これで足りるかを確認する。

### 4.2 絞り込みの詳細

CSV 出力と組み合わさって、最優先の要求を成立させている実装。

- 場所: `frontend/src/app/event/[id]/MemberTable.tsx` と `memberTableUtils.ts`（`matchesMemberTableFilter`）
- 絞り込める列: 名前・学年・学籍番号・学生メール・Discord・保険・アレルギー・**リアクション**（8列）
- 演算子: `contains`（部分一致。配列にはいずれかの要素が一致すれば真）／`equals`（完全一致）／`is`（真偽）
- リアクション列は配列のため `contains` が効く。「参加リアクションを押した人だけ」を選べる

**CSV は絞り込み後の行を出力する**（`table.getRowModel()`）。
したがって「イベント参加者だけを抽出して大学提出用に出す」という用途は、既に成立している。

## 5. 記録されていない負債

要求「長く使える（恐れは引き継ぎ失敗・メンテ不足・技術的負債）」に直結するもの。

- `members` が17列で「申請」と「部員」を兼ねる。1人1申請しか持てず、再入部・休会を表現できない。
- `members` への書き込みが5サービス6箇所に重複。楽観ロックの骨格が毎回手書きされている。
- 権限変更を記録する場所がない。誰がいつ誰を管理者にしたかが残らない。
- 名簿取得に上限がなく、全件を返す。
- 学年が申請時の値で固定される。進級の扱いが未定義。
