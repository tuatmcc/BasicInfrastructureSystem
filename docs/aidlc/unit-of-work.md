# 2.7 Units Generation — 作業単位

- 段階: Phase 2 Inception / 2.7
- 状態: **承認済み**（2026-11-01 改訂。前版は 2026-09-03 に承認）
- 入力: `requirements.md`・`components.md`（いずれも承認済み）

V1 を実装可能な単位に分ける。各単位は、マージした時点で `develop` が動く（CI が通る）ことを条件とする。
それを満たせない単位は、分け方が間違っている。

---

## 前提の改訂（2026-11-01）

前版は「本番が稼働中」を前提にしていた。2026-11-01 に依頼者に確認した結果、これは事実ではなかった。

- プロトタイプの Worker は停止済みで、公開していない
- 本番データベースにあるのは開発者とテスト用のアカウントだけで、**破棄してよい**
- 実際の利用者はまだいない。開発者もほぼ依頼者ひとり

前版の分け方は「稼働中の本番を壊さない」ための慎重さを含んでいた。
たとえば、旧ロール列と新しいロール表を並存させる期間を設けていたのはこのためである。
運用前の今はその慎重さが要らないため、U-3 と U-4 をまとめた。
一方で、**運用を始めた時点で本番になる**。運用開始までに満たすべき条件は「運用開始の条件」として下にまとめた。

`requirements.md` C-1（既存データを失わない）も、運用開始後から適用するように改めた。

---

## 分割の考え方

運用前のため、本番を止めないための制約は課さない。残すのは、壊れたときに原因を切り分けられることと、レビューできる大きさである。

- ひとつの単位で、互いに独立した大きな変更を混ぜない（例：権限判定の置き換えとスキーマ分離）
- セキュリティ上の欠陥を塞ぐ単位は、その欠陥が使われ始める単位より前に置く
- データの移行は要らない。運用開始時に本番データベースを作り直す

### U-2.5 ロール付与を偽装できないようにする — **U-3 に統合**（2026-11-01）

番号は、既存の記録からの参照を壊さないために欠番として残す。

**統合した理由と、前版の説明の訂正**

前版は「アプリが申告した役割を、データベースが実際の値と突き合わせる。アプリ層が侵害されても権限を偽装できないようにする」としていた。
2026-11-01 に確かめたところ、この方式で防げるのは**アプリのバグだけ**で、乗っ取られたアプリは防げなかった。

- 突き合わせるのは「申告された人の ID と役割が、表と一致するか」。乗っ取られたアプリが本物の管理者の ID を申告すれば一致する
- アプリ（`app_rls`）は `app_accounts` を更新でき、`role` 列も制限されていない。突き合わせ先そのものを書き換えられる

既存の `members` の突き合わせ（`app_private.enforce_member_workflow`）も同じで、守れているのはバグだけである。

依頼者と確認し、アプリの乗っ取りは保証の対象外とした（`requirements.md` C-4 改訂）。
そのうえで、申告を突き合わせるのではなく、**そもそも役割を申告させない**ことにした。
アプリはユーザー ID だけを伝え、データベースが自分で権限を調べる。
これは U-3 で RLS を書き換えるときに行うのが自然なので、U-3 に統合した。

### U-3 判定を置き換え、旧いロール列を外す — 実装・検証済み、レビュー待ち（2026-11-05）

| | |
| --- | --- |
| 満たす要件 | FR-4.3・4.4・4.5、C-4 |
| 内容 | ロール名で判定している17箇所を権限判定に置き換える。RLS ポリシー19箇所は、アプリが申告した役割（`app.current_user_role`）を見るのをやめ、ユーザー ID からデータベースが自分で権限を調べる形に変える（`app_private.has_permission`）。そのうえで `app_accounts.role` を削除する |
| 影響 | 判定の挙動が変わる |
| 完了条件 | ロール名で判定している箇所がひとつも残っていない。`app.current_user_role` を読む箇所がない。`app_accounts.role` が存在しない。管理者ロールを持つ部員が従来どおり操作できる |

アプリと RLS を同時に変える必要がある。片方だけでは権限が食い違う。

**データベースへ伝えるもの**（2026-11-01 決定。U-2.5 を統合）

- アプリが伝えるのはユーザー ID（`app.current_user_id`）だけにする。役割も権限も伝えない
- RLS は `app_private.has_permission(ユーザー ID, '権限名')` で判定する。この関数が、ユーザー ID → 部員 → ロール → 権限 をたどる。権限の正しい値は、この1か所で決まる
- `member_roles` への付与・剥奪も、`role.manage` を持つかをこの関数で判定する

community のデータベースについては U-10 を参照。

前版では列の削除を U-4 として分けていた。稼働中の本番で、新しい判定が動くのを確かめてから旧い経路を消すためである。
運用前の今は確かめる対象の本番がないため、ひとつにまとめた。
旧い列を残すと「どちらが正か」が曖昧な期間が延びる。

変更量は大きいため、PR は「アプリと RLS の置き換え」と「列の削除」の2つに分けてもよい。ただし両方そろうまでは完了としない。

**community の権限の扱い**（2026-11-01 決定）

分けた後の community のデータベースは、`member_roles` を読めない。そのため、U-3 の `has_permission` は community では使えない。
community は自分で権限を計算せず、**member が調べた権限の一覧を受け取って使う**。この取得経路と community 側の切り替えは U-10 に含め、member のテーブルへのアクセスを外す前に動作を確認する。U-10 完了時点で、他サービスのテーブルを直接読まずに community の権限判定が動くことを完了条件とする。
community の RLS は、その一覧を伝えられた値として判定する。

伝えられた値を信じる形に戻るが、C-4 の範囲（バグを防ぐ。乗っ取りは保証外）では問題ない。
権限を計算する場所が member の1か所に限られるので、計算を誤るバグが入る場所も1か所に限られる。

## 順序

依存関係で決まる部分と、選べる部分がある。

```
U-1 → U-2 → U-3                 ロールの土台（この順でなければならない）
                     ↓
                    U-5, U-6    引き継ぎと退部連動（U-3 完了後）

U-7 → U-8                     表示と一覧（上とは独立）

U-9                           内部整理（いつでも可。U-3 の前だと衝突が減る）

U-10 → U-11                   分離（運用開始の前の最後。他が安定してから）
```

### 推奨する順

1. ~~**U-9**~~ — 完了（#71）
2. **U-1 → U-2 → U-3** — ロールの土台。U-1・U-2 は完了、U-3 はレビュー待ち（U-2.5 を含む）。マージ後は U-5・U-6
3. **U-5・U-6** — 引き継ぎと退部連動。ここで運用上の欠陥が解消する
4. **U-7 → U-8** — 表示と一覧
5. **U-10 → U-11** — 分離。運用開始の前に行う（下の「決定事項」）

**U-5 までで、最も困っていること（引き継ぎがDB操作でしかできない）が解消する。**

## 運用開始の条件

運用を始める（実際の部員の情報を入れる）前に、次をすべて満たす。満たすまで公開しない。

- U-3 が完了している（データベースが、アプリの申告ではなくユーザー ID から権限を調べている）
- U-6 が完了している（退部者の権限が残らない）
- U-7 が完了している（在籍者以外の非公開情報を返さない）
- U-10・U-11 が完了している（運用後に回すと、データを保ったままの移行が要るため）
- 3つのワークスペースで `npm audit --omit=dev --audit-level=high` が通る
- 本番データベースを作り直し、プロトタイプのデータを残さない
- この時点から `requirements.md` C-1（本番データを失わない）を適用する。以降の変更はデータの移行を伴う

## 決定事項

### U-10・U-11 は運用開始の前に行う（2026-11-01、依頼者が決定）

前版では「可換性への投資で、運用上の困りごとは解決しない。後回しでよい」としていた。
ただし、それは稼働中の本番を前提にした判断だった。前提が変わったため、改めて比べて決めた。

| | 運用開始の前にやる | 運用開始の後にやる |
| --- | --- | --- |
| 移行の手間 | データがないため、スキーマを分けるだけで済む | データを保ったままテーブルを移し、接続資格情報を切り替える。メンテナンス時間が要る（`docs/hyperdrive-security.md`） |
| 運用開始の時期 | U-10・U-11 の分だけ遅れる。最も大きい単位である | 遅れない |

運用開始の日付に締め切りがないため、総作業量が小さい「前にやる」を選んだ。
代わりに、運用開始は U-10・U-11 の分だけ遅れることを受け入れる。
