# 2.7 Units Generation — 作業単位

- 段階: Phase 2 Inception / 2.7
- 状態: **改訂案・承認待ち**（2026-11-01）。前版は 2026-09-03 に承認
- 入力: `requirements.md`・`components.md`（いずれも承認済み）

V1 を実装可能な単位に分ける。各単位は、マージした時点で `develop` が動く（CI が通る）ことを条件とする。
それを満たせない単位は、分け方が間違っている。

---

## 前提の改訂（2026-11-01）

前版は「本番が稼働中」を前提にしていた。2026-11-01 に依頼者に確認した結果、これは事実ではなかった。

- プロトタイプの Worker は停止済みで、公開していない
- 本番データベースにあるのは開発者とテスト用のアカウントだけで、**破棄してよい**
- 実際の利用者はまだいない。開発者もほぼ依頼者ひとり

前版の分け方は「稼働中の本番を壊さない」ための慎重さを含んでいた。
たとえば、旧ロール列と新しいロール表を並存させる期間を設けていたのはこのためである。
運用前の今はその慎重さが要らないため、U-3 と U-4 をまとめた。
一方で、**運用を始めた時点で本番になる**。運用開始までに満たすべき条件は「運用開始の条件」として下にまとめた。

`requirements.md` C-1（既存データを失わない）も、運用開始後から適用するように改めた。

---

## 分割の考え方

運用前のため、本番を止めないための制約は課さない。残すのは、壊れたときに原因を切り分けられることと、レビューできる大きさである。

- ひとつの単位で、互いに独立した大きな変更を混ぜない（例：権限判定の置き換えとスキーマ分離）
- セキュリティ上の欠陥を塞ぐ単位は、その欠陥が使われ始める単位より前に置く
- データの移行は要らない。運用開始時に本番データベースを作り直す

## 単位

### U-1 ロールの器を作る — **完了**（#73）

| | |
| --- | --- |
| 満たす要件 | FR-4.2・4.3・4.6 |
| 内容 | ロール・権限・部員ロール・ロール権限のテーブルを作る。部員でない相手に付けられない制約を入れる |

既存の `app_accounts.role` はまだ残す。両方が並存する状態を作る（U-3 で解消する）。

### U-2 権限で判定する仕組みを作る — **承認済み・マージ待ち**（#76）

| | |
| --- | --- |
| 満たす要件 | FR-4.5、NFR-1.1 |

### U-2.5 ロール付与を偽装できないようにする

| | |
| --- | --- |
| 満たす要件 | C-4、NFR-1.1 |
| 内容 | `member_roles` への書き込みを、アプリが申告したロールだけで許さない。`members` と同じく、データベース側で実値と突き合わせる。突き合わせ先は最初から `member_roles` 自身（書き込む本人が `role.manage` を持つか）にする |
| 影響 | 追加のみ |
| 完了条件 | 申告だけでは付与できない。突き合わせに失敗した書き込みが拒否される |

**U-3 より前に必ず終わらせる。** U-1 のレビューで見つかった不足への対応。

前版では、突き合わせ先を一時的に `app_accounts` とし、U-4 の後で `member_roles` に替える予定だった。
U-3 と U-4 をまとめたため、すぐ消える列に向けた突き合わせを書く意味がなくなった。
U-1 が管理者全員に `admin` ロール（`role.manage` を含む）を付けているので、U-2.5 の時点で `member_roles` だけを見ても管理者は書き込める。

U-1 が入れたポリシーは `app.current_user_role` の値だけを見ている。

```sql
with check ((select current_setting('app.current_user_role', true)) = 'admin')
```

`members` にはこれに加えて `app_private.enforce_member_workflow` があり、
申告されたロールを `app_accounts` の実値と突き合わせている。アプリ層が侵害されても
権限を偽装できないようにするためで、これが C-4 の趣旨である。

`member_roles` は全権限の源泉であり、`members` より価値の高い標的でありながら、
現状その突き合わせがない。U-3 で判定を移すまでは誰もこのテーブルを使わないため
現時点の危険はないが、U-3 の前提として閉じておく必要がある。

### U-3 判定を置き換え、旧いロール列を外す

| | |
| --- | --- |
| 満たす要件 | FR-4.3・4.4・4.5 |
| 内容 | ロール名で判定している17箇所を権限判定に置き換える。RLS ポリシー19箇所も同様に、渡す識別子を権限へ変える。そのうえで `app_accounts.role` を削除する |
| 影響 | 判定の挙動が変わる |
| 完了条件 | ロール名で判定している箇所がひとつも残っていない。`app_accounts.role` が存在しない。管理者ロールを持つ部員が従来どおり操作できる |

アプリと RLS を同時に変える必要がある。片方だけでは権限が食い違う。

前版では列の削除を U-4 として分けていた。稼働中の本番で、新しい判定が動くのを確かめてから旧い経路を消すためである。
運用前の今は確かめる対象の本番がないため、ひとつにまとめた。
旧い列を残すと「どちらが正か」が曖昧な期間が延び、U-2.5 の突き合わせ先も二度書くことになる。

変更量は大きいため、PR は「アプリと RLS の置き換え」と「列の削除」の2つに分けてもよい。ただし両方そろうまでは完了としない。

## 順序

依存関係で決まる部分と、選べる部分がある。

```
U-1 → U-2 → U-2.5 → U-3         ロールの土台（この順でなければならない）
                     ↓
                    U-5, U-6    引き継ぎと退部連動（U-3 完了後）

U-7 → U-8                     表示と一覧（上とは独立）

U-9                           内部整理（いつでも可。U-3 の前だと衝突が減る）

U-10 → U-11                   分離（運用開始の前の最後。他が安定してから）
```

### 推奨する順

1. ~~**U-9**~~ — 完了（#71）
2. **U-1 → U-2 → U-2.5 → U-3** — ロールの土台。U-1 は完了、U-2 は #76 のマージ待ち、**次は U-2.5**
3. **U-5・U-6** — 引き継ぎと退部連動。ここで運用上の欠陥が解消する
4. **U-7 → U-8** — 表示と一覧
5. **U-10 → U-11** — 分離。運用開始の前に行う（下の「決定事項」）

**U-5 までで、最も困っていること（引き継ぎがDB操作でしかできない）が解消する。**

## 運用開始の条件

運用を始める（実際の部員の情報を入れる）前に、次をすべて満たす。満たすまで公開しない。

- U-2.5 が完了している（権限の偽装を防げないまま公開しない）
- U-6 が完了している（退部者の権限が残らない）
- U-7 が完了している（在籍者以外の非公開情報を返さない）
- U-10・U-11 が完了している（運用後に回すと、データを保ったままの移行が要るため）
- 3つのワークスペースで `npm audit --omit=dev --audit-level=high` が通る
- 本番データベースを作り直し、プロトタイプのデータを残さない
- この時点から `requirements.md` C-1（本番データを失わない）を適用する。以降の変更はデータの移行を伴う

## 決定事項

### U-10・U-11 は運用開始の前に行う（2026-11-01、依頼者が決定）

前版では「可換性への投資で、運用上の困りごとは解決しない。後回しでよい」としていた。
ただし、それは稼働中の本番を前提にした判断だった。前提が変わったため、改めて比べて決めた。

| | 運用開始の前にやる | 運用開始の後にやる |
| --- | --- | --- |
| 移行の手間 | データがないため、スキーマを分けるだけで済む | データを保ったままテーブルを移し、接続資格情報を切り替える。メンテナンス時間が要る（`docs/hyperdrive-security.md`） |
| 運用開始の時期 | U-10・U-11 の分だけ遅れる。最も大きい単位である | 遅れない |

運用開始の日付に締め切りがないため、総作業量が小さい「前にやる」を選んだ。
代わりに、運用開始は U-10・U-11 の分だけ遅れることを受け入れる。
