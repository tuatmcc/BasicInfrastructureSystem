# 2.6 Domain Design — 境界と構成

- 段階: Phase 2 Inception / 2.6
- 状態: **承認済み**（2026-09-03）
- 入力: `requirements.md`（承認済み）

要件を満たす構成を決める。テーブルの列定義までは踏み込まず、
**何をどこが所有し、境界をどう越えるか**を確定させる。

---

## 1. 所有権

「そのデータの不変条件を守る責任を持つのは誰か」で決める。読みたい人がいることは所有の理由にならない。

| スキーマ | 所有者 | テーブル |
| --- | --- | --- |
| `app_auth` | 認証（Better Auth） | user / session / account / verification |
| `community` | community | community_identities / community_memberships / event_messages |
| `member` | member | members / grades / member_directory_profiles / member_status_history / roles / role_permissions / member_roles / member_role_history |
| `app_api` | 公開読み取り | 名簿ビューなど。所有者は持たない |
| `app_private` | データベース内部 | トリガー関数 |

### 1.1 `app_accounts` の行き先

現在 `public.app_accounts(user_id, member_id, role)` は認証と業務をつなぐ。
`role` は member へ移す（`requirements.md` FR-4）ため、残るのは `user_id ↔ member_id` の対応だけになる。

**member が所有する。** 「この認証済みの人は、どの部員か」を知る責任は member にある。
community はこの対応を必要とするが、所有はしない（2.2 で述べる経路で問い合わせる）。

## 2. 境界の越え方

### 2.1 原則

- **他サービスのテーブルを直接読み書きしない。** 相手のAPIを呼ぶ。
- **境界を越える外部キーを作らない。** 識別子は値として持つ。
- 各スキーマへの接続は、そのサービスの資格情報でのみ行う。

### 2.2 必要な越境

現状の実測（`reverse-engineering.md` 2節）から、越境が必要なのは3つ。

| 呼び出し | 目的 | 現状 |
| --- | --- | --- |
| member → community | 入部申請・承認時に Discord 在籍を確認する | `community_memberships` を直接読んでいる |
| community → member | リアクション一覧に部員の詳細を出す | `members` ほかを直接読んでいる |
| 両サービス → 認証 | セッションが有効か確かめる | `app_auth.session` を直接読んでいる |

### 2.3 リアクション一覧の組み立て

越境の具体例。community が起点となり、member に問い合わせる。

1. community が Discord からリアクションを取得する（Discord ID の一覧）
2. community が自分の `community_identities` で Discord ID → 認証subject を引く
3. community が member API に認証subject の一覧を渡す
4. member が「在籍者のみ」の詳細を返す（`requirements.md` FR-3.2）
5. community が組み立てて返す

**4 が要件を満たす鍵になる。** 在籍していない人の詳細は member が返さないため、
community 側に「隠す」処理を書く必要がない。非公開情報が越境する経路自体が存在しなくなる。

### 2.4 通信方式

**型付きHTTPクライアント（`hc<App>`）を使う。** フロントエンドが既に採用している方式であり、
新しい仕組みを持ち込まない（`requirements.md` NFR-1.4・1.5 の「既存に倣う」）。

Cloudflare の Service Bindings は採らない。速度で有利だが、
サービスをどこで動かすかを Cloudflare に固定するため、可換性（NFR-2）と競合する。

## 3. ロールと権限

### 3.1 構造

```
部員 ──< 部員ロール >── ロール ──< ロール権限 >── 権限
```

- 部員とロールは多対多（FR-4.2）
- ロールと権限も多対多
- 部員に権限を直接与える経路を作らない（FR-4.3）

「管理者」はロールの一行にすぎない（FR-4.4）。

### 3.2 権限の定義（Q-1・Q-2 の決定）

**権限もロールへの割り当ても、すべてデータとして持つ**（2026-09-03 決定）。

権限は行として存在し、ロールとの対応も行として持つ。
コード側に権限の一覧を持たない。権限を存在させるのはデータベースの行だけである。

ただし、コードが名前で参照する権限は `share/permissions.ts` に書き出す（U-2）。
これは権限の正典ではなく、綴りの誤りをコンパイラに弾かせるための部分集合である。
データベースにあってコードにない権限は許す。逆は下の検査で失敗させる。

**この方式の弱点と対策**

コードが参照する権限名と、データベースにある権限名がずれても、コンパイル時に気づけない。
`member.read_private` を `member.readPrivate` と書き間違えると、
その判定は「誰も持っていない権限」を要求することになり、**常に拒否されるか、常に通る**。
どちらに転ぶかは実装次第だが、いずれも気づきにくい。

対策として、**コード中で使われている権限名が、すべてデータベースに存在することを検査する**。
これを自動で走らせ、ずれたら失敗させる（`requirements.md` NFR-1.1「制約は破れないよう強制する」）。

V1 で必要な権限は、要件から導くと6つ。

| 権限 | 用途 | 根拠 |
| --- | --- | --- |
| `member.read_public` | 他の部員の公開情報（名簿）を見る | FR-1.3 |
| `member.read_private` | 部員の非公開情報を見る | FR-1.4 |
| `member.review` | 入部申請を承認・却下する | 既存 |
| `member.edit` | 管理者として部員情報を修正する | 既存 |
| `role.manage` | ロールを付与・剥奪する | FR-5.1 |
| `event.manage` | イベント通知を作成・閲覧する | 既存 |
| `reaction.read` | リアクション一覧を見る | FR-2.1 |

粗い粒度に保つ（`requirements.md` の「ロールの増殖」への対策）。

**`member.read_public` を置く意味**（2026-09-03 追加）

名簿の閲覧は現在「在籍者かどうか」で判定している。これを権限にすると、
**全員が例外なくロール経由で権限を得る**形に統一できる。特別扱いの分岐が消える。

在籍者に自動で与える基本ロール（仮に「部員」）を1つ置き、そこに `member.read_public` を持たせる。
役職のロールはその上に重ねる。

これにより退部の扱いも揃う。基本ロールが外れれば名簿も見られなくなるため、
FR-4.7（退部でロールが外れる）を守るだけで名簿の締め出しも同時に成立する。
「退部者を名簿から締め出す」処理を別に書かなくてよい。

### 3.3 判定の書き方

```
呼び出し側:  権限を持つか（member.read_private を持つか）
書かない:    ロール名で判定（admin かどうか）
```

19箇所ある既存のロール名判定をこの形に置き換える（FR-4.5）。

RLS は、アプリが申告した役割を見るのをやめる。アプリはユーザー ID だけを伝え、
member のデータベースが `app_private.has_permission(ユーザー ID, '権限名')` で自分で権限を調べる（`requirements.md` C-4、2026-11-01 改訂）。
community は member から受け取った権限の一覧を使う（`unit-of-work.md` U-10）。

**判定のルール**（2026-11-01 決定）

- API ごとに、必要な権限で判定する。ロール名では判定しない
- 権限の名前は「データの種類.操作」にする（例：`event.manage`）
- データの中身（本人のものか、状態など）による違いは、権限を分けず、処理の中の条件で判定する
- 権限を分けるのは、実際に区別が必要になったときだけにする。分けるときは、今の保有者に新しい権限も渡し、誰の権限も変わらない状態から始める

### 3.4 守るべき不変条件

アプリではなくデータベース側で守る（`requirements.md` C-4、NFR-1.1）。

| 不変条件 | 根拠 |
| --- | --- |
| 部員でない相手にロールを与えられない | FR-4.6 |
| `role.manage` を持つ人が0人になる操作を拒否する | FR-5.2 |
| ロールの変更が履歴に残る。履歴は追記のみ | FR-5.3 |
| 退部するとロールが外れる | FR-4.7 |

最後の2つは、既存の `member_status_history` と同じ方式（トリガーが書き、アプリは書けない）にする。

### 3.5 ロール付与の読み取りはデータベースで絞らない（U-2 で決定）

`member_roles` の SELECT は、`app_accounts` と同じく `app_rls` に無条件で許す（`using (true)`）。
3.4 の「データベース側で守る」の例外として、範囲と理由をここに残す。

**理由**

- 権限は呼び出し元を解決する処理の中で読む。その時点ではまだ `app.current_member_id` が設定されていない。
  このため、本人の行に絞るポリシーでは結果が空になり、**全員の権限がゼロになる**。
  しかも見た目は権限のバグで、実際の原因である読み取り順序にはたどり着きにくい
- 絞っても守れるものがほぼない。`app_rls` は `app_accounts.role` を既に無条件で読めるので、
  アプリ層が侵害された時点で誰が管理者かは分かってしまう。
  また、ロールの付与は認可のための情報であり、部員の個人情報ではない。
  個人情報を守っているのは `members` のポリシーと名簿ビュー

**緩めないもの**

- 付与と剥奪（INSERT / DELETE）は今まで通り制限する。権限昇格につながるのはこちら。
  U-3 で、`role.manage` を持つかをデータベースがユーザー ID から調べる形に変える（`unit-of-work.md` U-3。U-2.5 を統合）

**この決定の帰結**

- 部員のロールを画面に出す API は、**誰に何を見せるかを API 側で絞る**。データベースは絞ってくれない
- U-3 で RLS ポリシーを権限ベースへ変えるとき、ポリシーの中から `member_roles` を参照してよい

**採らなかった案**

- 呼び出し元の解決を2つのトランザクションに分け、2つ目で `app.current_member_id` を設定してから読む。
  読み取りの順序という見えにくい前提に正しさを頼ることになる。
  順序を誤ったときの症状（全員の権限がゼロ）も原因にたどり着きにくい
- SECURITY DEFINER 関数で権限を返す。仕組みが増えるわりに、上の理由で守れるものがない

### 3.6 RLS の範囲（2026-11-09 決定）

権限の判定は API が行う。RLS は、API の判定を書き忘れたときの最後の守りとして、必要な所だけに絞る。

**原則**

1. **RLS は API より必ず緩くする。** API が許す操作を RLS が拒むことはない。
   RLS に拒まれた行は、エラーにならず黙って消える。API と食い違うと「0 件」に見え、原因にたどり着きにくい
2. **RLS が止めるのは、どの API でも起きてはならない次の2つだけ。**
   - 他人の個人情報が、部員を管理する権限のない人に渡ること
   - 権限が勝手に広がること

**表ごとの扱い**

| 表 | RLS | ルール |
| --- | --- | --- |
| `members`・`member_directory_profiles` | 守る | 読み書きできるのは、本人か、部員を管理する権限（`member.read_private`・`member.review`・`member.edit` のどれか）を持つ人（`app_private.is_member_manager`） |
| `member_status_history` | 守る（読み取り） | 同上。書き込みはトリガーだけ |
| `member_roles` | 守る（書き込み） | 付与と剥奪は `role.manage` を持つ人だけ。読み取りは誰でも（3.5） |
| `app_accounts` | 守る（`member_id` の書き込み） | 結び付けを外す、本人がロールのない部員に結び付ける（入部申請）、部員を管理する権限を持つ人が結び付ける（承認）の3つだけ。ポリシーでは変更前の値を見られないのでトリガーで確かめる |
| `event_messages`・`community_identities`・`community_memberships` | 守らない | アプリの接続ユーザーにすべて許す。判定は API |
| `grades`・`app_roles`・`permissions`・`role_permissions` | 守らない | 読み取りは誰でも。書き込みは migration だけ（接続ユーザーに権限を与えていない） |

`members` で、部員一覧の API は `member.read_private` を要求するが、RLS は `member.review` だけを持つ人にも読ませる。
原則1を守るために意図して緩くしている。細かい区別は API が行う。

整合性の決まり（3.4 の不変条件、入部の状態遷移のトリガー、外部キー）は RLS ではないので、この範囲とは別に、どの API から呼んでも破れないよう守り続ける。

## 4. 書き込みの共通化

`members` への書き込みが6箇所に重複している（NFR-1.4 違反）。
共通するのは次の骨格で、各サービスに固有なのは「何を変えるか」と「どの状態から遷移してよいか」だけ。

```
版番号と状態が一致する行だけを更新し、更新できなければ競合として返す
```

これをひとつの関数にまとめ、6箇所から呼ぶ。ロール変更にも同じ仕組みを使う。

## 5. 決定（Q-1〜Q-4）

| ID | 論点 | 決定 | 理由 |
| --- | --- | --- | --- |
| Q-1 | 権限の粒度 | 6つ（3.2） | 要件から導ける最小。粗く保ちロールの増殖を防ぐ |
| Q-2 | 権限をデータか定数か | **すべてデータ** | 依頼者の決定。権限の一覧を一箇所で見られ、対応も参照として持てる。名前のずれは検査で防ぐ |
| Q-3 | サービス間の通信方式 | 型付きHTTP（`hc<App>`） | 既存に倣う。Service Bindings は Cloudflare に固定するため採らない |
| Q-4 | 申請と部員を分けるか | **V1では分けない** | 下記 |

### Q-4 の理由

要件に再入部・休会がない（`requirements.md` 4.3）。
分けることは、いま必要のない構造を先に作ることであり、
「予防的な抽象化を持たない」（NFR-1.2）に反する。

ただしロールを部員に紐づけたため、**部員の行の寿命が権限の寿命になる**。
分けない以上、退部でロールが外れること（FR-4.7）を必ず守る。
守らなければ、退部した人が再入部したときに以前の権限が復活する。

再入部・休会が要件になった時点で分割を検討する。その際に移行が必要になることは受け入れる。

## 6. 移行

運用開始前のため、既存データを保つ必要はない（`requirements.md` C-1、2026-11-01 改訂）。
前版では「本番が稼働中」を前提に、データを保ったまま段階的に移す手順にしていた。

| 順序 | 内容 | 状態 |
| --- | --- | --- |
| 1 | ロール関連のテーブルを作る | 完了（U-1） |
| 2 | 現在の `app_accounts.role` からロールを作り、割り当てる | 完了（U-1） |
| 3 | 判定を権限ベースに置き換え、`app_accounts.role` を削除する | U-3。前版の 3 と 4 をまとめた |
| 4 | スキーマを分割し、越境をAPI呼び出しに置き換える | U-10。運用開始の前に行う（`unit-of-work.md`「決定事項」） |

3 と 4 は同時に行わない。片方が壊れたときに原因を切り分けられなくなる。

運用を始めた後のスキーマ変更は、C-1 に従ってデータを保ったまま行う。

## 7. セッションの検証（Q-5 の決定）

**即時失効を維持する。** 認証サービスに問い合わせて、セッションが生きているか毎回確かめる（2026-09-03 決定）。

署名済みトークンだけで判定すれば越境は消えるが、トークンの有効期限（現在7日）まで
失効が効かなくなる。退部者や権限を外した相手のアクセスを、その場で止められることを優先する。

| 方式 | 即時失効 | 越境 | 採否 |
| --- | --- | --- | --- |
| 認証サービスへ問い合わせる | できる | リクエストごとに1回 | **採用** |
| 署名済みトークンだけ | できない（最大7日遅れる） | なし | 不採用 |
| 有効期限を短くして更新する | 数分の遅れ | 更新時のみ | 不採用（実装が増える割に中途半端） |

**設計上の含意**

- 認証サービスは、セッションの有効性を答える経路を持つ（トークンそのものは返さない）
- 各サービスの認証ミドルウェアが、この問い合わせを行う唯一の場所になる
- 問い合わせ先が落ちているとき、**通さない**（fail closed）。既存の起動時検査と同じ方針

**代償**

リクエストごとに越境が1回増える。現在は同一データベース内の読み取りで済んでいる。
将来 `app_auth` を物理的に別データベースへ移すと、この経路がネットワーク越しになる。
そのときに遅延が問題になれば、有効期限の短縮を再検討する。
