# 2.3 Requirements Analysis — 要件

- 段階: Phase 2 Inception / 2.3
- 状態: **承認済み**（2026-09-03）
- 入力: `intent.md`（承認済み）、`reverse-engineering.md`（承認済み）

要求を、満たしたかどうか判定できる形にしたもの。
設計（テーブル構成・API・画面）はここでは決めない。

各要件には識別子を付ける。実装とテストはこの識別子を参照する。

---

## 0. 前提

`intent.md` で決まっており、ここで議論しない。

- 管理者は必ず部員である。システム管理だけを行う非部員は考慮しない。
- ロールは部員に紐づく。権限はロールに紐づく。部員に直接権限を与えない。
- システムのロールは Discord のロールから独立。V1では同期しない。
- V1 でロールの階層と積集合による絞り込みは作らない。ただし後から足せる形にする。
- 出欠・会費・イベント参加履歴は範囲外。

---

## 1. 機能要件

### FR-1 部員情報

| ID | 要件 | 判定 |
| --- | --- | --- |
| FR-1.1 | 部員は自分の申請内容を提出・修正できる | 申請後に自分の画面で内容が変更でき、変更が保存される |
| FR-1.2 | 部員は自分の公開情報（興味・取り組み）を編集できる | 在籍中に編集でき、名簿に反映される |
| FR-1.3 | 部員は他人の公開情報だけを見られる | 他人の学籍番号・緊急連絡先が、API・画面のいずれからも取得できない |
| FR-1.4 | 管理者は部員の非公開情報を見られる | 学籍番号・緊急連絡先・保険・アレルギーを閲覧できる |

### FR-2 大学提出資料（最優先）

| ID | 要件 | 判定 |
| --- | --- | --- |
| FR-2.1 | 管理者はイベントのリアクションから参加者を一覧できる | 誰がどのリアクションを押したかが一覧に出る |
| FR-2.2 | 一覧を柔軟に操作できる（FR-6 参照） | FR-6 の各項目を満たす |
| FR-2.3 | 絞り込んだ結果を大学提出に使える形で取り出せる | 表計算ソフトで開ける形式で、絞り込み後の行だけが出力される |
| FR-2.4 | 出力に大学提出で必要な項目が含まれる | 氏名・学年・学籍番号・緊急連絡先・保険・アレルギーを含む |

> FR-2.1・2.3・2.4 は既存実装が満たしている（`reverse-engineering.md` 4.1・4.2）。V1では維持が要件であり、作り直さない。

### FR-6 一覧の操作

大学提出資料を作る作業を、画面上で完結させるための要件。
出力（FR-2.3）は操作した結果に対して行われる。

| ID | 要件 | 判定 | 現状 |
| --- | --- | --- | --- |
| FR-6.1 | 任意の列で絞り込める | 絞り込みの対象外となる列がない | 8列のみ対応 |
| FR-6.2 | リアクション種別で絞り込める | 特定のリアクションを押した人だけに絞れる | 対応済み |
| FR-6.3 | 任意の列で並べ替えられる | 昇順・降順を切り替えられる | 対応済み |
| FR-6.4 | 列の表示・非表示を切り替えられる | 不要な列を隠した状態で出力できる | **未対応** |
| FR-6.5 | 列の並び順を変えられる | 提出資料に合わせた順序で出力できる | **未対応** |
| FR-6.6 | 操作した結果がそのまま出力される | 絞り込み・並べ替え・列構成が出力に反映される | 行のみ反映 |

> FR-6.4〜6.6 は、大学提出資料が「必要な列だけを、必要な順で」求める場合に効く。
> 現状は21列すべてが固定の順序で出力されるため、提出前に表計算ソフト側で加工する必要がある。

### FR-3 在籍状態による表示

| ID | 要件 | 判定 |
| --- | --- | --- |
| FR-3.1 | リアクション一覧に、システム未登録の人も並ぶ | 部員行を持たない人が一覧から欠落しない |
| FR-3.2 | 在籍者だけ詳細が表示される | 申請中・却下・退部・未登録の人の非公開情報が表示されない |
| FR-3.3 | 詳細を持たない人は「未登録」と分かる | 一覧上で在籍者と区別でき、絞り込みの対象にもなる |
| FR-3.4 | 退部すると、その人の非公開情報が一覧から消える | 退部処理だけで消える。別の操作を必要としない |

### FR-4 ロールと権限

| ID | 要件 | 判定 |
| --- | --- | --- |
| FR-4.1 | ロールを作成・変更・削除できる | 実行後に一覧へ反映される |
| FR-4.2 | 部員に複数のロールを与えられる | 1人が2つ以上のロールを同時に持てる |
| FR-4.3 | 権限はロールに属する | 部員に直接権限を与える手段が存在しない |
| FR-4.4 | 管理者はロールの一つとして表現される | 「管理者」を特別扱いする分岐がコード上に存在しない |
| FR-4.5 | 権限の判定は権限名で行う | ロール名で判定している箇所が存在しない |
| FR-4.6 | 部員でない人はロールを持てない | 部員行のない相手にロールを与えようとすると拒否される |
| FR-4.7 | 退部するとロールが外れる | 退部処理だけで外れる。別の操作を必要としない |

### FR-5 引き継ぎ

| ID | 要件 | 判定 |
| --- | --- | --- |
| FR-5.1 | 権限を持つ人が、他の部員に同じ権限を渡せる | データベースを直接操作せずに完了する |
| FR-5.2 | 権限を持つ人が誰もいない状態を作れない | 最後の1人を外そうとすると拒否される |
| FR-5.3 | 誰がいつ誰のロールを変えたかが残る | 変更後に記録を参照でき、消去・改竄ができない |

## 2. 品質要件

`intent.md` 6.3 の品質目標を、判定できる形にしたもの。

### NFR-1 お手本となること

| ID | 要件 | 判定 |
| --- | --- | --- |
| NFR-1.1 | 重要な制約は破れないよう強制されている | 型・テスト・データベース制約のいずれかで、違反が実行前か実行時に止まる |
| NFR-1.2 | 予防的な抽象化を持たない | 差し替える予定のないものに、差し替えるための層が存在しない |
| NFR-1.3 | コードを読めば意図が分かる | 説明を読まなくても、実装から何をしているか追える |
| NFR-1.4 | 関心が分離されている | ひとつの関心を変えるとき、触る場所がひとつに定まる |
| NFR-1.5 | カプセル化されている | 所有者の外から不変条件を壊せない。内部表現を知らなくても使える |

> 「設計判断の理由を文書に残すこと」は要件から外した（2026-09-03）。
> 過剰な説明は不要であり、コードを読んで分かることが目標。
> なお判断の経緯は本ディレクトリ（`docs/aidlc/`）に残るため、別途コード側に書く必要はない。

#### NFR-1.4・1.5 の基準

既存実装に手本があるため、新しい方式を持ち込まずこれに倣う（2026-09-03、依頼者による）。

| 手本 | 何を分離・隠蔽しているか |
| --- | --- |
| `CommunityProvider` とアダプタ | プロバイダ固有の形式・制限をアダプタに閉じ込め、ポートは中立に保つ |
| `app_api.member_directory_entries` | 非公開列をビューに含めない。公開経路から構造的に取得できない |
| `app_private` のトリガー | 状態遷移の不変条件をデータベース側で守る。アプリは破れない |
| RLS ポリシー | 誰が何を見られるかをデータ層で決める。各サービスが個別に判断しない |
| `createRlsDatabase` | トランザクション境界と識別子の受け渡しを内側に隠す。呼び出し側は意識しない |

**現状これに反している箇所**（V1で解消する）

- `members` への書き込みが5サービス6箇所に重複し、楽観ロックの骨格が毎回手書きされている（NFR-3.2）
- 権限判定が19箇所に散らばり、ロール名で書かれている（FR-4.5）
- サービスが他サービスのテーブルを直接読み書きしている（NFR-2.3）

この3つは、いずれも「ひとつの関心を変えるのに複数箇所を触る」状態であり、NFR-1.4 違反として扱う。

### NFR-2 可換であること

| ID | 要件 | 判定 |
| --- | --- | --- |
| NFR-2.1 | 認証を差し替えるとき、認証モジュール以外を変更しない | ドメイン側のコードとテーブル定義に、認証固有の型・テーブル参照がない |
| NFR-2.2 | コミュニティ基盤（Discord）を差し替えるとき、アダプタ以外を変更しない | ポートの型に provider 固有の形式・制限が現れない |
| NFR-2.3 | auth / community / member がデータを共有しない | あるサービスのテーブルを、他のサービスが直接読み書きしない |
| NFR-2.4 | 将来それぞれを別データベースへ移せる | サービス境界を跨ぐ外部キーが存在しない |

> NFR-2.3・2.4 は同一データベース内でスキーマを分けることで満たす。物理的な分離は V1 では行わない（`intent.md` 4.5）。

### NFR-3 長く使えること

| ID | 要件 | 判定 |
| --- | --- | --- |
| NFR-3.1 | 引き継ぎがデータベース操作を必要としない | 運営に必要な操作がすべて画面から完了する |
| NFR-3.2 | 同じ手順が複数箇所に散らばっていない | 同一の処理が3箇所以上に手書きで複製されていない |
| NFR-3.3 | 破壊的な操作の前に検証が働く | 誤った状態遷移・権限のない操作が、実行前に拒否される |

## 3. 制約

守らなければならない条件。要件ではなく前提。

| ID | 制約 |
| --- | --- |
| C-1 | 既存の本番データを失わない。稼働中の会員・管理者・イベント通知を保持する |
| C-2 | 認証テーブルは Better Auth が所有する。ドメインの列を足さない |
| C-3 | 非公開情報は、公開用の経路から構造的に取得できないこと（列として存在させない） |
| C-4 | アプリケーションが申告する権限を、データベースが検証する |
| C-5 | 実行ロールは superuser でも BYPASSRLS でもないこと |

C-2〜C-5 は既存実装が満たしている。維持が条件。

## 4. V1 の範囲

### 4.1 作るもの

- FR-4 ロールと権限（全体）
- FR-5 引き継ぎ（全体）
- FR-3.2・3.3・3.4 在籍状態による表示の制御
- FR-6.1・6.4・6.5・6.6 一覧の操作（絞り込みの全列対応、列の表示切替と並び替え、出力への反映）
- NFR-2.3・2.4 サービス間のデータ共有の解消

### 4.2 維持するもの（作り直さない）

- FR-1 部員情報
- FR-2.1・2.3・2.4 大学提出資料
- FR-3.1 未登録者も一覧に並ぶ
- FR-6.2・6.3 リアクションでの絞り込み、並べ替え
- C-2〜C-5

### 4.3 作らないもの

- ロールの階層構造
- ロールの積集合による絞り込み・通知
- サークル専用 SNS
- 出欠・会費・イベント参加履歴
- 物理的なデータベース分離

## 5. 未確定

設計段階（2.6）で決める。

| ID | 論点 |
| --- | --- |
| Q-1 | 権限をどの粒度で定義するか。V1でいくつ必要か |
| Q-2 | ロールと権限の対応を、データとして持つか定数として持つか |
| Q-3 | サービス間の通信方式。HTTP か Service Bindings か |
| Q-4 | `members` の「申請」と「部員」を分けるか（再入部・休会の扱い） |

Q-4 は V1 の範囲外の課題だが、ロールを部員に紐づける以上、部員行の寿命が権限の寿命になる。
分けるかどうかで移行の内容が変わるため、設計前に判断する。
